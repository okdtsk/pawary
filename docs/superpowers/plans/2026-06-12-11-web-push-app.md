# Pawary Plan 11: Web Push — App + Service Worker — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Client side of Web Push: migrate the PWA to a custom service worker (injectManifest) that preserves ALL current caching/update behavior and adds push + notification-click handling, plus a Notifications settings card for per-device opt-in. EN/JA.

**Spec:** `docs/superpowers/specs/2026-06-12-web-push-design.md` §3. Conventions as prior plans. Frontend verification: `npm run typecheck -w app && npm run build -w app && npm run test -w app`; ALSO `npm test` from root (the worker suite re-verifies the unchanged API; run worker part sharded if local).

**THE RISK in this plan is the SW migration.** Before touching anything, read `app/vite.config.ts` in full and inventory the CURRENT generated-SW behavior: `registerType: "prompt"`, every `workbox.*` option (runtime caching rules, navigateFallback and its denylist, cleanupOutdatedCaches, etc.), and how `app/src/features/pwa/UpdatePrompt.tsx` consumes `virtual:pwa-register/react`. The custom SW must reproduce ALL of it. Any rule you cannot port 1:1, STOP and report rather than approximating.

**Locked decisions:**

| Decision | Choice |
|---|---|
| Strategy | `VitePWA({ strategies: "injectManifest", srcDir: "src", filename: "sw.ts", registerType: "prompt", manifest: <unchanged>, injectManifest: { globPatterns: <match current precache> } })` |
| SW source | `app/src/sw.ts` using workbox-* modules (vite-plugin-pwa bundles them; add `workbox-precaching`, `workbox-routing`, `workbox-strategies`, `workbox-core` as devDependencies only if not already transitive — check `npm ls` first) |
| Update flow | preserve prompt-style updates: `precacheAndRoute(self.__WB_MANIFEST)`, `self.skipWaiting()` ONLY on the `SKIP_WAITING` message (this is what `virtual:pwa-register/react` sends), `clientsClaim()` per current behavior — verify against the generated `dist/sw.js` BEFORE migrating (build once and read it) |
| Push handlers | `push`: parse `event.data.json()` `{title, body, url}`, `showNotification(title, { body, data: { url }, icon: "/pwa-192x192.png", badge: <only if a badge asset already exists> })`. `notificationclick`: close, focus an open client and navigate it to `data.url`, else `openWindow(url)` |
| Subscribe flow | Settings card: feature-detect (`"serviceWorker" in navigator && "PushManager" in window && "Notification" in window`); enable = `Notification.requestPermission()` → `getRegistration()` → `pushManager.subscribe({ userVisibleOnly: true, applicationServerKey: urlBase64ToUint8Array(publicKey from GET /api/push/public-key) })` → POST `/api/push/subscriptions` `{endpoint, p256dh, auth, tz: deviceTzOffsetMin()}` (keys from `sub.toJSON().keys`); disable = `sub.unsubscribe()` + DELETE. Status detection on mount: `pushManager.getSubscription()` |
| iOS note | shown when `!window.matchMedia("(display-mode: standalone)").matches` and UA is iOS: localized hint that push requires installing to Home Screen |
| i18n | new `Messages.push` section: title, enable, disable, enabled-status, unsupported, denied (permission), iosInstallHint, error. EN/JA |
| Placement | A "Notifications" Card on `SettingsHome` (between sections list and data export) — no separate route |

**Tasks:**

### Task 1: SW migration (no push yet)
Inventory current behavior (vite config + built `dist/sw.js` + UpdatePrompt). Create `app/src/sw.ts` reproducing precache + runtime caching + update flow; switch vite config to injectManifest; ensure TS setup for the SW file compiles (`WebWorker` lib via `/// <reference lib="webworker" />` and `declare let self: ServiceWorkerGlobalScope`; exclude or include in tsconfig as needed so `npm run typecheck -w app` stays clean). Verify: build output contains `sw.js` with the precache manifest injected (`grep __WB_MANIFEST` absent, precache entries present); existing app tests green. Commit: `refactor: migrate pwa to custom service worker via injectmanifest`

### Task 2: Push + click handlers in the SW
Add `push` and `notificationclick` handlers per the locked decisions. Pure-logic helpers (payload parse guard) testable if separable; otherwise verified by build + Task 4 manual checklist. Commit: `feat: handle push and notification clicks in the service worker`

### Task 3: API helpers + i18n
`app/src/api/push.ts`: `getPushPublicKey()`, `subscribePush(sub, tz)`, `unsubscribePush(endpoint)` (plain api() calls); `app/src/lib/pushClient.ts`: `urlBase64ToUint8Array`, feature detection, `getCurrentSubscription()`, `enablePush()` / `disablePush()` composing the browser+API flow. i18n `push` section in all three files. Unit-test `urlBase64ToUint8Array` (`app/test/push.test.ts`). Commit: `feat: add push client helpers and i18n`

### Task 4: Settings card
`app/src/features/pwa/NotificationsCard.tsx` on SettingsHome: status-aware (unsupported / denied / disabled / enabled), enable/disable buttons with pending spinners, iOS install hint, error toasts. Commit: `feat: add notifications opt-in card to settings`

### Task 5: Verification sweep
Typecheck/build/app tests + root test (worker sharded locally); spec sweep; manual post-deploy checklist appended to the PR description (enable on a device, complete a schedule with nextDueAt in the past, wait for cron, verify push + click-through; iOS standalone check). No push/deploy without the user.
